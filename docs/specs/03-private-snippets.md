# 03 — Private Snippets: шифрование и безопасное обращение

Статус: core реализован · Зависит от: — · Остаток: Secure Reference, предупреждения и защита reveal-окна

## Зачем

product.txt §5, §22. Сейчас «Private» — только маска на экране: текст лежит в `cards.body`
открыто, индексируется FTS5, попадает в WAL и в буфер обмена без ограничений. Импорт Sticky Notes
уже положил в базу 19 карточек, похожих на пароли. Это долг безопасности, а не фича.

## Поведение

1. Карточка типа Private хранит **метку** (видимую: «Wi-Fi офис») и **секрет** (зашифрован).
2. На слое, в поиске, в библиотеке виден только значок замка и метка. Секрет не показывается
   ни в превью, ни в сниппетах, ни в подсказках.
3. «Показать» расшифровывает секрет на `reveal_seconds` (по умолчанию 5 с), затем прячет.
   Любая потеря фокуса слоя прячет сразу.
4. «Копировать» копирует секрет **без показа**. Буфер очищается через 30 с, если там всё ещё наш
   секрет. Секрет не попадает в историю буфера Windows (Win+V) и в облачный буфер.
5. Поиск находит Private только по метке и тегам.
6. Захват: префикс `секрет:`/`private:` или распознанный секрет (`sticky::looks_secret`) делает
   карточку Private; в баре это видно чипом «Private», его можно снять одним кликом до сохранения.
   Первая строка → метка, остальное → секрет; однострочный текст → метка «Без названия».
7. Предупреждение при создании, если текст похож на данные, которые нельзя хранить здесь
   (номер карты по Луну, seed-фраза из 12/24 слов BIP-39, `-----BEGIN ... PRIVATE KEY-----`):
   «Такие данные лучше хранить в менеджере паролей» + кнопка «Сделать Secure Reference».
8. **Secure Reference** — отдельный тип: текст-указатель («Production VPN → Bitwarden /
   Infrastructure / VPN») и опционально ссылка/приложение, которое открывается кнопкой
   («Открыть Bitwarden»). Секрета не хранит.
9. В настройках (вкладка «Данные») явно написано: встроенное хранилище не заменяет
   Bitwarden / 1Password / KeePass; что именно защищено и от чего (см. «Модель угроз»).

## Модель угроз

Защищает от: чтения файла базы/бэкапа/копии профиля другим пользователем или на другой машине;
случайного показа на экране и в скриншоте; попадания в историю буфера и в поисковый индекс.

Не защищает от: вредоносного кода, запущенного под тем же пользователем Windows (DPAPI отдаст ему
ключ); человека за разблокированным компьютером (можно нажать «Показать»).

## Данные

```sql
ALTER TABLE cards ADD COLUMN secret BLOB;       -- DPAPI ciphertext, только для private
-- для private: title = метка, body = '' , tags как обычно
```

В текущем core-срезе используется Windows DPAPI непосредственно для каждого секрета с
дополнительной энтропией `card.id`. Поэтому отдельного plaintext-ключа рядом с базой нет, а
скопированная база не расшифровывается другим пользователем Windows. Переход на отдельный
AES-256-GCM ключевой файл можно сделать позже, если понадобится переносимый экспорт.

Шифрование: Windows DPAPI (`CryptProtectData` / `CryptUnprotectData`) с дополнительной
энтропией, включающей `card.id` (секрет нельзя переставить в другую карточку).

Миграция существующих Private-карточек (однократно, в транзакции):
1. для каждой: `card::private_parts` — метка = заголовок или первая строка, **если она не похожа
   на секрет** (`card::fits_label`: ≤ 60 символов, без `=`, слов pass/key/token/secret/пароль/ключ,
   `root@`, `BEGIN`, длинных токенов с цифрами и IP-адресов), иначе «Private» и весь текст — секрет;
2. `body = ''`, `secret = encrypt(...)` — триггер FTS переиндексирует без секрета;
3. `PRAGMA secure_delete = ON` на время миграции, затем `wal_checkpoint(TRUNCATE)` и `VACUUM`,
   чтобы открытый текст не остался в свободных страницах и WAL. В обычной работе — `secure_delete = FAST`.

Первый core-срез оставлял меткой любую первую строку; при открытии базы такие метки
(не проходящие `fits_label`) возвращаются в секрет той же миграцией.

## Реализация

- Новый модуль `vault.rs`: `protect(id, &str) -> Vec<u8>` и `unprotect(id, &[u8]) -> String` через
  DPAPI; plaintext не попадает в модель `Card` и живёт в UI только во время reveal.
  Буфер с открытым текстом обнуляется после использования (без крейта: `SecureZeroMemory`).
- Буфер обмена: своя запись через Win32 (`OpenClipboard`/`SetClipboardData`) с форматами
  `CanIncludeInClipboardHistory = 0`, `CanUploadToCloudClipboard = 0`; очистка через 30 с — фоновый поток
  ждёт таймер и
  проверяет `GetClipboardSequenceNumber()`.
- Показ секрета: пока открыт — `SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE)` для окна слоя
  (опция «Скрывать от записи экрана», по умолчанию включена), затем `WDA_NONE`.
- Поиск: `store::search` уже не отдаёт сниппет для private; после миграции body пуст — индекс чист.
- Импорт Sticky Notes: карточки, распознанные как Private, сразу пишутся зашифрованными.

## Производительность

- Ключ не загружается до первого показа/создания секрета: запуск не меняется.
- `decrypt` ≤ 2 мс, `CryptUnprotectData` один раз за сессию ≤ 10 мс, вне первого кадра.

## Критерии приёмки

- [ ] После миграции `findstr /c:"<секрет>"` по `ebb.db`, `-wal`, `-shm` ничего не находит
      (тест на временной базе: вставить, мигрировать, прочитать байты файлов).
- [ ] Поиск по слову из секрета не находит карточку; по метке — находит.
- [ ] «Копировать» кладёт секрет в буфер, Win+V его не показывает, через 30 с буфер пуст
      (если пользователь не скопировал что-то своё).
- [ ] `vault.key`, скопированный другому пользователю Windows, не расшифровывается.
- [ ] Показ длится `reveal_seconds` и прячется при потере фокуса.
- [ ] Private из импорта не проходит через открытый текст на диске (проверка байтов временной базы).
- [ ] Бенч: первый кадр и память в простое в пределах бюджета README.

## Не делаем

## Открытые вопросы

- DPAPI привязан к профилю Windows: переустановка = потеря секретов. Нужен ли экспорт
  секретов под паролем (PBKDF2/Argon2 → отдельный файл)? Предлагаю: да, в 07, опционально.
- Credential Manager вместо файла ключа? Проще резервировать, но виден в «Диспетчере учётных
  данных». Предлагаю файл + DPAPI.
